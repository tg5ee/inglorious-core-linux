# Contributing

## Adding another Glorious keyboard

Only the GMMK 3 HE 75% ANSI (`342d:e3de`) is supported and tested. Other boards
that use the same firmware protocol should be a modest port. Boards that do not
are a reverse-engineering project. This guide covers both. It is written so you
can hand it to a coding agent along with your board.

The keyboard stores settings in flash. A wrong write persists across replugs.
Read the safety rules at the end before sending anything to real hardware.

### 1. Identify the board

Plug it in and get its USB ID:

```sh
lsusb | grep -i 342d
```

Then list its vendor HID collections. This only reads sysfs; it sends nothing
to the keyboard.

```sh
for d in /sys/class/hidraw/hidraw*; do
  grep -qi 342d "$d/device/uevent" || continue
  echo "$d $(grep HID_ID "$d/device/uevent") $(od -An -tx1 -N5 "$d/device/report_descriptor" | tr -d ' ')"
done
```

The supported board shows three hidraw nodes. The config port is the one whose
descriptor starts `06ffff0902` (usage page 0xFFFF, usage 0x02). Input report 5
events use a second 0xFFFF collection, usage 0x01, which sits inside another
interface's descriptor rather than at its start (on this board it shares a node
with consumer controls, descriptor `050c0901a1`). If your board has a node
starting `06ffff0902`, it is very likely the same protocol.

### 2. Find the board in Glorious Core's device list

Glorious Core (Windows, Electron) describes every supported model in
`renderer-process/database/SupportDevice.DB`, a newline-delimited JSON file
inside its `app.asar`. Extract it from your own copy of Core. Do not commit any
Glorious Core files, code or images to this repository.

The Core installer is Inno Setup 7, which `innoextract` cannot unpack. What
worked: `7z x` the installer, LZMA2-decompress the resulting `[0]` payload, then
carve the `app.asar` out of it by finding its `{"files":{` header (the four
little-endian u32 values before it are `4, header size, pickle size, JSON
length`). `npx @electron/asar extract app.asar out/` then unpacks it.

Each DB line has `vid`, `pid` (wired, then 2.4 GHz dongle, then bootloader where
present), `routerID`, `devicename`, `img` and `deviceInfo.SyncData.LEDPosition`.
The `routerID` decides how much work this is:

- `Magneton`: same handler as the supported board. This covers the GMMK 3 HE
  65/75/100% ANSI and ISO and the GMMK 3 Pro HE (wired and wireless). Expect
  mostly tables and a device list.
- Anything else (`Gmmk3Series`, `GmmkSeries`, …): a different handler class in
  `main/index.js`. Its command set must be read from that JS before any code is
  written here.

The per-model key layout lives in `main/index.js` too: search for
`imagePath: "Keyboard_<img>"` using the DB entry's `img` value.

### 3. Code changes

Where the code is tied to one board:

- `src/device.rs`, `Transport::open`: matches `0x342d`/`0xe3de` and names it in
  errors. Replace the hardcoded PID with a small table of supported models
  (PID, display name, layout) and carry the detected model through.
- `src/tables.rs`: `PHYSICAL_KEYS` maps key names to the firmware's physical key
  numbers for the ANSI 75% grid only. Add the new layout's numbers from Core's
  device class. Do not assume they match the 75% numbering; check.
- `src/ui/widgets.rs`: the on-screen keybed geometry is hand-drawn for 75%.
- `src/ui/mod.rs`: the Device screen's name and ID string.
- `assets/device.png` / `assets/device.svg`: generated by
  `packaging/device_svg.py`. Draw your own; do not use Glorious renders.

`packaging/70-glorious.rules` already covers every `342d` device, so the udev
rule needs no change. Wireless dongle PIDs may behave differently over 2.4 GHz.
Start with the wired PID.

Keep `--dry-run` working for the new model, and run:

```sh
cargo test
cargo clippy --all-targets -- -D warnings
```

### 4. Testing on hardware

1. Build and use `--dry-run` until the TX lines look right for your model.
2. Run read-only commands first (`info`, profile and firmware reads). Check the
   replies make sense. A get needs at least 20 ms after its set, or it returns
   the previous reply.
3. Then test writes **one kind at a time**: lighting preset, per-key RGB,
   actuation, rapid trigger. Watch the board and confirm each before the next.
4. Treat keymap, advanced keys, calibration and factory reset as untested even
   on the supported board. Leave them for last, and say in your PR whether you
   tried them.

### Safety rules

- Never add host-driven animation: no timer or streamed per-key writes. Each
  per-key frame is a flash write, and the wear cost is unknown.
- Never run the app as root; use the udev rule.
- Note in your PR exactly which features you verified on your board.

### Prompting an agent

A suggested starting prompt:

> Read CONTRIBUTING.md. Add support for my Glorious `<model>` (`342d:<pid>`).
> Its SupportDevice.DB entry is: `<paste>`. Its layout from Core's
> `main/index.js` is: `<paste>`. Make `device.rs` match a model table instead
> of a hardcoded PID, and add the layout to `tables.rs`. Do not send any write
> to the keyboard until I approve that write type.
